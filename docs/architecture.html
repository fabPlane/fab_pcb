FabPlane PCB · architecture and hosting

How FabPlane PCB fits together

FabPlane PCB is a browser front end for KiCad. KiCad itself runs headless, one process per open project, and speaks protobuf over a socket. Everything a user sees is a browser page that renders what that process reports and sends edits back through KiCad's own commit machinery. This page explains each hop, then what it takes to put the whole thing in front of many users.

Five packages in the browser and one Bun process on the server side. The dotted path is the bridgeless mode, where the tab dials KiCad's own WebSocket listener.

Three things make this work at all, and each was verified against the source rather than assumed.

  • KiCad has a headless server. kicad-cli api-server loads a project without a window and answers every API command from the same handlers the desktop app uses. One process holds one project: one schematic, one board, any number of library items.
  • The wire format is small. nng's REQ/REP over a unix socket: an 8‑byte handshake, then frames of a 9‑byte header and a protobuf ApiRequest whose payload is a google.protobuf.Any. Bun speaks it in about 150 lines, no native modules.
  • Edits go through KiCad's commit API. BeginCommit, CreateItems/UpdateItems/DeleteItems, EndCommit. KiCad validates, serialises, and keeps the undo stack. The page never writes a file.

A request, end to end

sequenceDiagram
  participant T as Browser tab
  participant B as Bridge
  participant K as kicad-cli api-server
  T->>B: POST /sessions { path: foo.kicad_pro }
  B->>K: spawn with --socket ipc:///tmp/kicad/api-<id>.sock
  B->>K: Ping until AS_OK, then GetServerInfo
  K-->>B: kicad_token, events_socket_url
  B->>K: subscribe SUB0 to the events socket
  B-->>T: { sessionId, kicadToken }
  T->>B: WebSocket /ws?session=id
  T->>B: binary frame: 4-byte id + ApiRequest(Any: GetItems)
  B->>K: same bytes, framed for nng
  K-->>B: ApiResponse(Any: GetItemsResponse)
  B-->>T: 4-byte id + response bytes
  K-->>B: Event(DocumentChanged) on PUB socket
  B-->>T: reserved id 0xFFFFFFFF + Event bytes
The bridge never parses a request; it only adds a correlation id so several tabs can pipeline on one socket, and copies event frames to every tab of the session.

Latency is not the reason for the bridge. Measured over 500 pings on one machine: 0.035 ms straight to the unix socket, 0.081 ms through the bridge, 0.091 ms on KiCad's own WebSocket transport. The bridge exists because a browser cannot open a unix socket or spawn a process, and because someone has to own file access and cleanup.

Editing and undo

sequenceDiagram
  participant U as User
  participant S as Item store (tab)
  participant K as KiCad
  U->>S: drag R1 to a new position
  S->>S: patch R1 optimistically, redraw
  S->>K: BeginCommit
  S->>K: UpdateItems [R1 with new position]
  K-->>S: canonical R1 (KiCad re-read the fields)
  S->>K: EndCommit "Move R1"
  K-->>S: DocumentChanged { updated: [R1], revision: n+1 }
  U->>S: Ctrl+Z
  S->>K: Undo
  K-->>S: DocumentChanged { updated: [R1], revision: n+2 }
  S->>K: GetItemsById [R1]
The page keeps a normalised store keyed by KIID and applies its own edit immediately; the canonical item from KiCad replaces it. Undo is KiCad's own stack; a client-side inverse-patch stack remains as the fallback for old servers.

Selection, hover, visible layers and the active layer never leave the page. Those are the 15 commands the API marks GUI-only, and in a web UI that state belongs to the tab, not to the process.

The renderer never ships a font engine or a pad tessellator: KiCad computes glyph outlines and pad polygons, so the page draws exactly what the plotter draws.

This is measurable. A pixel-diff harness renders the board headlessly and compares it against KiCad's own SVG export at the same scale. The board differs in 0.27% of pixels, 0.05% within a one-pixel tolerance. Getting there required three additions to the API itself: barcode geometry, knockout-text polygons and the composed dimension string, because a client cannot recompute those from the data KiCad used to send.

One interface, two very different routers. The JS router is instant on small boards and fails outright on dense or four-layer ones; Freerouting routes those but takes minutes and needs Java.

Hosting for many users

The unit of isolation is already right: one KiCad process per open project, owned by a session, reaped when idle. Multi-user hosting is a question of who spawns those processes, where the files live, and who is allowed to talk to which session. Three shapes, in order of effort.

smallest · a team on one box

One bridge, one machine

  • Reverse proxy in front (Caddy, nginx) terminating TLS and doing login with OIDC or basic auth; the bridge stays on loopback.
  • One WORKSPACE_ROOT per user, chosen from the proxy's identity header; the bridge already confines the file API to a root.
  • SESSION_IDLE_TIMEOUT_SEC reaps servers nobody has open. Freerouting runs in the same box; cap concurrent jobs.
  • Fits until CPU spikes from DRC and routing start colliding: roughly 10 to 20 active users on a modern 8‑core.
medium · a company

Container per session

  • The Linux image in packages/kicad-patches/docker already runs kicad-cli api-server headless; add the bridge as the entrypoint and you have a session pod.
  • A small session controller (or the bridge itself in "scheduler" mode) creates a container per opened project, routes /ws?session= to it, and stops it on idle.
  • Files on a per-user volume or synced from object storage at open and save; the project stays on local disk while a session is live because KiCad reads its own files for jobs.
  • Resource limits per pod: memory and CPU quotas make one person's autoroute invisible to everyone else.
largest · a product

Kubernetes with a scheduler

  • Same pod, plus a control plane: an API that maps user → project → session, with presence, and a queue for heavy jobs (Freerouting, gerbers on large boards) on separate nodes.
  • Autoscale on session count, not requests; sessions are long-lived and stateful.
  • Warm pool of started servers to hide the 0.6–1.1 s cold start; the first launch on a fresh node is slower while the binary is scanned.
  • Object storage as the source of truth, versioned per save, so a crashed pod loses nothing past the last save.

What must stay private

KiCad's listener has no origin check and its only credential is a shared token. That is fine on loopback and inside a pod, and not fine on a network. Keep kicad-cli reachable only from its own bridge; let the bridge, behind the proxy, be the thing that decides who may attach to a session. The bridgeless ws:// mode is for a single trusted user on their own machine, or for a future where KiCad gains origin and per-connection auth.

Two people, one board

Nothing in the stack forbids two tabs on one session, and most of it already works: KiCad keys in-flight commits by client_name, so each tab can have its own open commit, and every commit's DocumentChanged reaches every tab, which re-reads exactly the changed items. What is missing is the human layer.

sequenceDiagram
  participant A as Alice's tab
  participant B as Bob's tab
  participant K as kicad-cli (one process)
  A->>K: BeginCommit (client alice)
  B->>K: BeginCommit (client bob)
  A->>K: UpdateItems [R1]
  B->>K: UpdateItems [C3]
  A->>K: EndCommit
  K-->>A: DocumentChanged updated:[R1]
  K-->>B: DocumentChanged updated:[R1]
  B->>K: EndCommit
  K-->>A: DocumentChanged updated:[C3]
  K-->>B: DocumentChanged updated:[C3]
Independent items merge naturally. Two edits to the same item are last-writer-wins, which is what desktop KiCad does too, only there it is one person.
  • Presence and cursors are a bridge feature: broadcast selection and camera per client over the same WebSocket as a text control message.
  • Soft locks on selected items, held in the bridge, prevent two people dragging the same footprint. KiCad does not need to know.
  • Undo is the hard part: KiCad has one undo stack per document, so Bob's Ctrl+Z can undo Alice's move. Either scope undo to "your own last commit" in the bridge, or accept shared undo and show whose step it is; the history panel already labels commits by client.

What exists, what to build

existssessions with one process per project, idle reaping, a confined file API, event relay, SSE, a Linux image that runs headless, route jobs with cancel, a token on the listener to buildlogin and per-user workspace roots at the proxy or bridge, a session controller for containers, object storage sync at open and save, per-session quotas, a job queue for routers and big exports, presence and soft locks, a policy for shared undo to leave aloneKiCad's process model: one project per process is the isolation boundary you want, and it is what the whole API assumes

A good first milestone for hosting is the smallest shape with real login: a reverse proxy, per-user roots, and idle reaping. It changes nothing in the code, exercises everything that matters, and tells you the actual per-user cost before you build a scheduler.
